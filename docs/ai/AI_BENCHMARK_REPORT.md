# TalentLens AI benchmark report

**Run:** 2026-11-19 (latest run after the JD-title change to semantic queries), `python benchmarks/run_benchmark.py`, Windows 11, Python 3.11.9, CPU only.
**Raw output:** `benchmarks/results/latest.json` and `latest.md`. Every number below is copied from that output.

## Read this first: limits of this benchmark
* **The data is synthetic and the labels are by construction.** There are 72 pairs (6 job descriptions × 12 resume
  archetypes) generated by `benchmarks/dataset.py`. The relevance labels, gold skills and gold sections were assigned
  by the same author who wrote the taxonomy and the engine. This is **not** an independent human annotation, so absolute
  scores are optimistic. Most metrics test whether the engine behaves as designed. The benchmark is
  useful for **comparing engines** and **catching regressions**. It does **not** show accuracy on real resumes or
  any link to hiring outcomes.
* The resumes are short and cleanly worded, and the PDFs are generated text PDFs, which is why
  extraction scores 100%. Real, layout-heavy PDFs will be harder.
* There are 12 candidates per role and 6 roles, so one rank swap moves the metrics noticeably.
* Timings were taken on a developer laptop where ONNX inference is unusually slow (about 60 sentences/s). They aren't a
  production figure; see the Performance section in `AI_UPGRADE_PLAN.md`.

## Dataset
Each role has these 12 archetypes, with relevance from 0 to 3:

| Relevance | Archetypes |
| --- | --- |
| 3 | strong (skills described in use), alias (the same, written with aliases), multi-page |
| 2 | paraphrase (responsibilities in other words), partial, badly formatted (no headings) |
| 1 | related technologies, ambiguous (skills only listed), keyword-stuffed, missing a mandatory skill |
| 0 | negated ("no experience with …"), irrelevant (containing a trap phrase) |

Trap phrases test known false positives: "Express Logistics Ltd", "go-to-market", "R&D", "C-level" and "rest of the team".
A self-check fails the run if any filler text accidentally contains a skill outside the gold labels.

## Results

### Ranking (mean over 6 roles)
| Engine | NDCG@5 | P@3 | Pairwise accuracy | Must-have accuracy |
|---|---:|---:|---:|---:|
| v2.0 (original) | 0.709 | 0.667 | 0.752 | 0.917 |
| v3 lexical (improved, no embeddings) | 0.945 | 1.000 | 0.876 | 1.000 |
| v3 hybrid (+ MiniLM ONNX) | **0.955** | **1.000** | **0.921** | 1.000 |

* **v2's main failure:** in all 6 roles it ranked the **"ambiguous"** resume (skills only listed, unrelated job)
  **first**, above the genuinely strong candidates. Skill coverage rewards keyword lists. v3 ranks strong, alias and
  multi-page first in every role.
* **Must-have accuracy** compares the "all recruiter must-haves met" flag with the gold labels (v2 used `must_have_missing`).
  v2 misses the negated resume, because "No experience with Python" counts as Python for v2.
* v3 *also* treats skills in the JD's "Requirements:" lines as mandatory. Against the must-have-only gold, that broader
  flag agrees 0.792 of the time. This is a deliberate design difference, not an error: the partial and related resumes
  *are* missing JD requirements.
* **Semantic matching adds:** a pairwise accuracy increase from 0.876 to 0.921 and NDCG@5 from 0.945 to 0.955. The gain
  comes mostly from paraphrase resumes moving above keyword-only ones.

### Skill extraction (all 72 resumes, micro-averaged)
| Extractor | Precision | Recall | F1 | False positives | of which trap phrases |
|---|---:|---:|---:|---:|---:|
| v2 (taxonomy matching) | 0.942 | 1.000 | 0.970 | 20 | 2 |
| v3 (+ negation handling) | 0.994 | 1.000 | 0.997 | 2 | 2 |

The 18 false positives removed by v3 are negated mentions. **The 2 remaining false positives are a known weakness:**
"Express Logistics Ltd" (an employer) is detected as the Express framework by both extractors, because the case-sensitive
alias `Express` has no context check. Recall is 1.0 because the gold labels use the taxonomy's own vocabulary, which is optimistic.

### Consistency
All three engines are **deterministic and order-invariant**: the same scores and ranks are produced when the candidate order is shuffled.

### Component correlation (v3 lexical, 72 resumes)
| | required | experience | projects | lexical |
|---|---:|---:|---:|---:|
| required | 1.00 | 0.81 | 0.71 | 0.28 |
| experience | 0.81 | 1.00 | 0.82 | 0.00 |
| projects | 0.71 | 0.82 | 1.00 | −0.02 |
| lexical | 0.28 | 0.00 | −0.02 | 1.00 |

**Double counting is real.** Required evidence, experience and projects are strongly correlated on this dataset
(0.71–0.82), so together they carry more of the score than their nominal 60% suggests. They are kept separate
because they explain *where* evidence was found, but the default weights should be re-examined on real data.

## Conclusions
1. On this synthetic set, v3 fixes v2's most serious ranking flaw (keyword lists outranking real experience) and its
   negation blind spot, while keeping determinism.
2. Semantic matching gives a smaller, consistent gain in pairwise ordering. It's optional, and its absence is reported in the UI.
3. Open weaknesses: context-free case-sensitive aliases ("Express"), correlated components, and labels that aren't
   independent. **Next step for credibility:** have 2 or more people independently label a set of real, consented or
   public-domain resumes, then re-run this script against those labels.
